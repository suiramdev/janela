# 0001. Generate the Xcode project from `project.yml`

- **Status:** Superseded by [0024](0024-tauri-client-shell.md) and
  [0025](0025-monorepo-tooling.md)
- **Date:** 2026-08-12

> There is no Xcode project to generate. The two problems this ADR existed to solve
> — a project file that does not merge and that coding agents corrupt — are gone
> rather than solved. Its underlying requirement survives in
> [0025](0025-monorepo-tooling.md): the fast path must be fast enough to run on
> every change.

## Context

Janela is a macOS app, so it needs an `.xcodeproj` to produce a signed, notarized
bundle with entitlements and an asset catalog. But `project.pbxproj` is a
generated-looking file that is nonetheless usually committed, and it has two
properties that matter here:

1. **It does not merge.** Two branches that both add a file conflict, and the
   conflict is unreadable. Resolving it by hand corrupts projects routinely.
2. **Coding agents damage it.** Object IDs are 96-bit hex keys with cross
   references. An agent editing it textually will produce a file that opens but is
   subtly wrong.

This repository is explicitly meant to be worked on by both humans and agents, so
(2) is not a hypothetical.

Prior art is split: cmux checks in `cmux.xcodeproj` and maintains pbxproj entries
by hand for its SPM packages, which its own contributor docs describe as a manual
step (see [`../research/prior-art-2.md`](../research/prior-art-2.md) § 1.1). That
is a real cost we can avoid.

## Decision

`project.yml` is the source of truth. `Janela.xcodeproj` is generated by
[XcodeGen](https://github.com/yonaskolb/XcodeGen) and **gitignored**.

All logic lives in `Packages/JanelaKit`, a local SPM package. The app target links
exactly one product (`JanelaApp`) and contains one Swift file. Consequently:

- Adding, moving, or deleting a source file changes nothing in `project.yml`.
- `make build` and `make test` never touch Xcode and complete in seconds.
- CI asserts that no `.xcodeproj/project.pbxproj` is committed.

## Consequences

**Good.** Project structure diffs are readable YAML. Merge conflicts in project
structure essentially disappear. An agent can add a file by writing a file. The
fast path (`swift build`) is fast enough to run on every change.

**Bad.** Contributors must run `make generate` after cloning and after any
`project.yml` change; forgetting produces a confusing "no such module" error. This
is documented in `AGENTS.md` and `docs/development.md`, and `make open` regenerates
first to make the common path safe.

**Also bad.** XcodeGen is an extra tool to install, and one more thing that can
break on an Xcode upgrade. It is a single Homebrew formula and `scripts/bootstrap.sh`
installs it, which we judged acceptable.

## Alternatives considered

**Commit the `.xcodeproj`.** The default. Rejected because of merge conflicts and
agent corruption, both of which we expect to hit weekly rather than yearly.

**Tuist.** More capable: caching, module graph validation, a real manifest
language. Rejected as too much machinery for a project with two Xcode targets. Its
graph features would duplicate what SPM target dependencies already enforce. This
is the option to reconsider if the module count grows substantially.

**SPM-only, no Xcode project.** Attractive, and it works for a plain executable.
Rejected because bundling, entitlements, asset catalogs, notarization and SwiftUI
previews all become manual. We would end up rebuilding a worse XcodeGen.

## Revisit when

- The module count passes roughly twenty, or build times make caching worthwhile —
  then evaluate Tuist.
- SPM gains first-class app-bundle, entitlement and notarization support — then
  drop the generator entirely.
